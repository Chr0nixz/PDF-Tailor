# PDF-Tailor 后续开发路线图

## 1. 文档目的

这份路线图基于当前仓库已经实现的功能，而不是从零开始规划 MVP。

当前产品已经具备：

- 本地 PDF 加载与渲染
- 单页裁剪框创建、移动、缩放和吸附
- 预设尺寸、9 宫格定位、边距输入
- 多页缩略图、多选和批量应用
- 预览与导出
- 撤销 / 重做、复制 / 粘贴、键盘微调
- 单元测试、E2E 冒烟测试和 CI

因此，后续开发重点应从“补齐基础能力”切换为两件事：

1. 增加更有区分度的新功能
2. 显著降低重复操作成本，提高使用便捷性

## 2. 当前产品判断

### 2.1 已经稳定的基础能力

以下能力已经适合作为后续迭代基座：

- 基于 `pdfjs-dist` 的文档加载和当前页渲染
- 基于 Zustand 的每页独立裁剪状态和历史记录
- 基于 Worker 的预览 / 导出管线
- 多页缩略图虚拟列表
- 关键主流程自动化测试

### 2.2 目前最明显的短板

从现有代码和交互看，当前短板主要在以下方面：

- 重复操作仍偏多，缺少“模板化”和“批量规则化”
- 导出反馈较弱，长任务没有更细粒度进度和取消能力
- 旋转页 `Redraw` 仍然受限
- UI 更偏桌面工程工具，正式产品化程度还不够
- 对真实复杂文档的覆盖面还不够广

## 3. 迭代目标

建议把后续版本目标定义为：

- `v1.1`：把常见裁剪任务做得更快
- `v1.2`：把复杂 PDF 和大文档做得更稳
- `v1.3`：把裁剪工具扩展为更完整的 PDF 页面处理工作台

## 4. 优先级原则

后续需求建议按以下原则排序：

1. 优先减少高频重复操作，而不是先做低频大功能
2. 优先补齐现有流程中的明确短板，而不是扩到全新产品线
3. 优先做能复用现有数据模型和导出链路的功能
4. 谨慎引入 OCR、云同步、账户体系等会明显改产品边界的需求

## 5. 第一阶段：易用性增强

建议周期：2 到 3 周

这一阶段应优先做投入小、收益高、对现有架构侵入较低的功能。

### 5.1 裁剪模板与参数记忆

优先级：最高

建议能力：

- 保存当前页裁剪配置为命名模板
- 模板包含裁剪框、模式、预设尺寸、定位方式、边距参数
- 支持模板重命名、删除、覆盖保存
- 自动记住最近使用的纸张尺寸、单位、导出模式、缩放方式

为什么先做：

- 当前产品已经支持复制 / 粘贴和批量应用，但仍然是一次性工作流
- 模板和偏好持久化能直接减少重复设置成本
- 可以先用 `localStorage` 落地，不需要后端

建议涉及模块：

- `src/store/usePdfStore.ts`
- `src/types/index.ts`
- `src/components/PropertiesPanel.tsx`
- 新增 `src/utils/persistence.ts`

验收标准：

- 刷新页面后仍保留用户偏好
- 可一键将模板应用到当前页或选中页
- 模板失败或数据损坏时可自动回退

### 5.2 批量操作范围增强

优先级：最高

建议能力：

- 支持 `Shift` 连续选择页面
- 支持按页码范围选择，例如 `1-5, 8, 10-12`
- 支持按条件选择页面，例如“已裁剪”“未裁剪”“旋转页”
- 批量清空裁剪
- 批量复制模板到符合条件的页面

为什么先做：

- 当前已有多选和应用到全部页，但批量范围控制还比较粗
- 真实文档中最常见的痛点就是“只处理一部分页”

建议涉及模块：

- `src/store/usePdfStore.ts`
- `src/components/PageSidebar.tsx`
- `src/components/PageThumbnail.tsx`
- 新增批量操作工具条组件

验收标准：

- 不依赖键盘也能完成页码范围批量操作
- 大于 100 页文档中批量选择仍然流畅
- 批量操作作为单个历史快照可撤销

### 5.3 导出体验补强

优先级：高

建议能力：

- 导出范围选择：当前页 / 选中页 / 全部页
- 导出文件策略：单个 PDF / 按页拆分 / ZIP 打包
- 导出进度百分比
- 支持取消正在进行的导出
- 导出完成后展示结果摘要

为什么先做：

- 当前导出能力够用，但大文档体验偏黑盒
- 用户对导出阶段的可控性和反馈会非常敏感

建议涉及模块：

- `src/components/ExportDialog.tsx`
- `src/workers/pdfExportWorker.ts`
- `src/workers/workerTypes.ts`
- `src/utils/pdfOperations.ts`

验收标准：

- 50 页以上文档导出时有明确进度反馈
- 用户可以取消导出且 UI 状态正确恢复
- 拆分导出和 ZIP 命名规则清晰稳定

### 5.4 产品化与交互抛光

优先级：高

建议能力：

- 统一中文文案，或增加中英切换
- 把空态文案从“阶段说明”改为正式产品引导
- 补充首次使用引导和快捷键提示
- 优化小屏布局，把三栏改为抽屉或标签页式结构
- 增加按钮禁用原因提示，而不是仅灰掉

为什么先做：

- 当前交互已经可用，但产品完成度还不够
- 小屏和新用户体验会直接影响试用反馈

建议涉及模块：

- `src/components/DropZone.tsx`
- `src/components/Header.tsx`
- `src/components/MainLayout.tsx`
- `src/index.css`

验收标准：

- 宽度较小的窗口下仍可完成完整裁剪流程
- 首次用户不看 README 也能理解主要操作路径

## 6. 第二阶段：核心能力补强

建议周期：3 到 5 周

这一阶段的目标是把当前“可用”推进到“复杂场景也可靠”。

### 6.1 旋转页 `Redraw` 支持

优先级：最高

当前状态：

- 已裁剪的 `90°/270°` 页面会禁用 `Redraw`

建议能力：

- 补齐旋转页在导出时的裁剪区域映射
- 在预览和最终导出中统一使用相同规则
- 为 0°、90°、180°、270° 都补测试

为什么重要：

- 这是当前最明确的功能缺口之一
- 该问题直接影响复杂扫描件和办公文档

建议涉及模块：

- `src/utils/pdfOperations.ts`
- `src/utils/documentWarnings.ts`
- `src/components/PreviewModal.tsx`
- `src/components/ExportDialog.tsx`
- `src/utils/pdfOperations.test.ts`
- `e2e/app.spec.ts`

验收标准：

- 旋转页裁剪后可成功 `Redraw`
- 预览结果和最终导出结果一致
- 旧的风险提示只在真正不支持的场景出现

### 6.2 自动裁边与内容检测

优先级：高

建议能力：

- 自动检测页面内容边界
- 一键去白边
- 统一白边值
- 批量对选中页执行自动裁边

为什么重要：

- 这是最能节省手工框选时间的功能
- 对扫描文档、教材、票据、讲义场景特别有价值

实现提示：

- 第一版可先基于 canvas 像素做简单边界检测
- 先覆盖黑白或高对比文档，再逐步增强

建议涉及模块：

- 新增 `src/utils/autoCrop.ts`
- `src/components/PropertiesPanel.tsx`
- `src/hooks/usePdfRenderer.ts`
- 相关测试文件

验收标准：

- 对常见扫描 PDF 能稳定识别主要内容区域
- 支持应用后再手动微调

### 6.3 大文档性能与内存治理

优先级：高

建议能力：

- 缩略图缓存上限和淘汰策略
- 预览文档和主文档的资源释放监控
- 导出前估算任务成本并提示
- 更细粒度的“Large document mode”

为什么重要：

- 当前缩略图会持续保留 `dataUrl`
- 文档页数和文件大小上来后，内存风险会更明显

建议涉及模块：

- `src/hooks/useThumbnails.ts`
- `src/hooks/usePdfRenderer.ts`
- `src/components/Header.tsx`
- 新增性能测试样例

验收标准：

- 100 页以上文档下内存波动可控
- 缩略图滚动和页切换无明显恶化

## 7. 第三阶段：工作流扩展

建议周期：4 到 6 周

这一阶段应建立在前两阶段完成之后。

### 7.1 页面级处理工具

建议能力：

- 页面旋转
- 页面删除
- 页面重排
- 页面拆分和合并

价值判断：

- 这能让产品从“裁剪工具”向“轻量 PDF 页面工具”扩展
- 但复杂度更高，应晚于模板、自动裁边和旋转兼容

### 7.2 会话恢复与项目文件

建议能力：

- 自动恢复上次未导出的裁剪状态
- 导出 / 导入项目配置 JSON
- 支持把同一套设置应用到后续相似文档

价值判断：

- 适合较长编辑流程
- 对频繁处理标准化材料的用户特别有价值

### 7.3 PWA 与离线增强

建议能力：

- 安装为桌面应用
- 最近文档工作区入口
- 离线使用优化

价值判断：

- 适合作为后续体验增强项
- 不应早于核心编辑和导出能力补强

## 8. 暂不建议优先投入的方向

以下能力并非没有价值，但不适合当前优先级：

- OCR
- 注释编辑
- 云端账户体系
- 在线协作
- AI 总结 / 翻译类旁支能力

原因：

- 会明显偏离当前产品主线
- 难以复用现有核心代码积累
- 对当前最核心的“裁剪效率”和“导出可靠性”帮助不直接

## 9. 研发排期建议

如果按单人或小团队节奏推进，建议采用以下顺序：

### 9.1 `v1.1`

目标：

- 模板和偏好持久化
- 批量操作范围增强
- 导出体验补强
- 正式化 UI 文案和小屏布局

发布判断：

- 用户可明显减少重复手工设置
- 多页文档操作路径更清晰

### 9.2 `v1.2`

目标：

- 旋转页 `Redraw`
- 自动裁边
- 大文档性能治理
- 更完整的复杂文档测试集

发布判断：

- 复杂 PDF 不再明显掉链子
- 真实扫描文档场景开始具备明显优势

### 9.3 `v1.3`

目标：

- 页面级处理工具
- 会话恢复
- 项目配置导入导出

发布判断：

- 产品从单点裁剪工具升级为轻量 PDF 工作台

## 10. 测试补强建议

为了支撑后续迭代，建议同步补以下测试：

- Firefox / WebKit E2E 冒烟
- 旋转页 `Redraw` 的单测和 E2E
- 大文档导出和取消导出测试
- 模板持久化测试
- 自动裁边纯函数测试
- 导出范围和 ZIP 拆分测试

## 11. 建议结论

当前版本最值得做的，不是盲目扩更多 PDF 功能，而是先把现有流程做得更省事、更稳定。

建议后续开发顺序固定为：

1. 模板、偏好记忆、批量范围、导出反馈
2. 旋转页 `Redraw`、自动裁边、大文档性能治理
3. 页面重排、拆分合并、会话恢复等扩展能力

如果只能挑一项立即开工，建议优先做“裁剪模板 + 批量范围增强”，因为它对现有用户的效率提升最直接，且能最大程度复用当前已经完成的状态模型与交互结构。
